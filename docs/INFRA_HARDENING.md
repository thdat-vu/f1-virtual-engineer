# Self-hosted infra hardening — Redis + RabbitMQ

Practical threat model + checklist for the broker/cache stack on a small VPS. **Read this before exposing any port to a public interface.**

The goal isn't paranoia — it's that the cheapest paths to root on this stack are well-known and trivially automated by scanners. The hardening below is the minimum that survives drive-by traffic.

## Redis

### What can go wrong

| # | Failure mode | What an attacker actually does | Severity |
|---|---|---|---|
| R1 | Bind to `0.0.0.0` with no password | `CONFIG SET dir /var/spool/cron/crontabs && CONFIG SET dbfilename root && SAVE` writes a cron file → root shell on next minute. There's a public CVE-style exploit with this exact payload from 2015; scanners still hit Redis daily. | **Critical** |
| R2 | Password set, but bound to a public port | Brute-force or token leak from a CI log. Same exploitation as R1 once authed. | High |
| R3 | No `maxmemory` | One large key (or a runaway `LPUSH` loop) ballons RAM until the kernel OOM-kills the whole VPS — Redis goes down with the API and the worker. | High |
| R4 | Persistence enabled when not needed | AOF rewrite spikes I/O; AOF file grows until disk fills (the original VPS pain that started this whole conversation). | Medium |
| R5 | `CONFIG`, `FLUSHALL`, `FLUSHDB` accessible | An authed-but-compromised client can wipe the cache or flip persistence to write to a malicious path. | Medium |
| R6 | `decode_responses=True` + naive eval of cached values | Inserting a crafted string in cache → SSRF / template injection if the consumer trusts the type. | Low |

### What this repo does about each

| | Mitigation | Where |
|---|---|---|
| R1, R2 | No `ports:` mapping on the redis service. Only the docker network can reach 6379. | `docker-compose.staging.yml` |
| R1, R2 | `requirepass` enforced via `${REDIS_PASSWORD:?...}` — compose refuses to start if unset. | same |
| R3 | `--maxmemory 256mb --maxmemory-policy allkeys-lru` | same |
| R4 | `--save "" --appendonly no` (cache-only mode) | same |
| R5 | `--rename-command CONFIG <random>` plus FLUSHALL/FLUSHDB rename. | same |
| R6 | `redis_cache.py` keeps `decode_responses=False` and JSON-encodes values explicitly. | `backend/core/redis_cache.py` |

### What's still on you (the operator)

- Strong `REDIS_PASSWORD` — 32+ random bytes, generated by `openssl rand -base64 32`. Never reuse a password used elsewhere.
- Don't add a `ports: ["6379:6379"]` for "convenience." Use `docker compose exec redis redis-cli -a "$REDIS_PASSWORD"` if you need the CLI.
- If the VPS is multi-tenant or shared, also `ufw deny 6379` and confirm Docker isn't punching a hole through iptables (it sometimes does on `host` network mode).
- Rotate the password if it's ever printed in CI logs or pasted in chat. Treat it like an SSH key.

## RabbitMQ (incoming with #139)

### What can go wrong

| # | Failure mode | What an attacker actually does | Severity |
|---|---|---|---|
| Q1 | Default `guest:guest` user accessible from outside `localhost` | RabbitMQ helpfully restricts `guest` to localhost by default, but `loopback_users.guest = false` in many tutorials disables that. Now `guest:guest` works from anywhere. | **Critical** |
| Q2 | Management UI on `:15672` exposed publicly | UI accepts the broker user. Compromised UI = full broker control = consume queues, drain DLQ, declare new exchanges. | High |
| Q3 | No vhost separation between apps | A bug in any app sharing the broker can read/write our queues. | Medium |
| Q4 | Unbounded queue depth | Producer outpaces consumer, queue grows until disk fills (RabbitMQ persists by default). Same OOM/disk-full pattern as Redis R3/R4. | High |
| Q5 | DLQ unmonitored | Real failures pile up silently; first sign is when you go look. | Medium |
| Q6 | No TLS on AMQP (`amqp://` instead of `amqps://`) | Credentials sent cleartext. Fine intra-VPS, dangerous over the public internet. | High in prod, low intra-VPS |
| Q7 | Erlang cookie default value | Multi-node clustering is implicitly authed by `~/.erlang.cookie`. Default values mean any node can join your cluster. Single-node deploys aren't affected. | Low for us today |

### What #139 will do about each

| | Mitigation | Where |
|---|---|---|
| Q1 | Disable the `guest` user; create a dedicated `apex` user with explicit permissions on a dedicated `/apex` vhost. | `docker-compose.staging.yml` + `rabbitmq-defs.json` |
| Q2 | Management UI port `15672` not mapped publicly. Same exec-pattern as Redis: `docker compose exec rabbitmq rabbitmqctl ...` or tunnel via SSH. | compose |
| Q3 | Dedicated vhost `/apex`, all queues + exchanges declared inside it. | compose + bootstrap |
| Q4 | `x-max-length` on each queue (e.g. 10k messages) + `x-overflow: reject-publish`. Producer sees `MessageNack`, won't blow disk. | task module |
| Q5 | Dedicated DLQ-worker container that reads the DLQ and emits structured logs + bumps `/metrics.workers.failed_24h`. | `backend/tasks/dlq_consumer.py` |
| Q6 | TLS deferred — single-VPS deployment puts AMQP on the docker bridge, never on the public internet. Note this in the compose file. | compose |
| Q7 | Single-node only for now. If we ever cluster, regenerate the cookie. | runbook entry |

### What's still on you (the operator)

- Strong `RABBITMQ_DEFAULT_PASS` (or whatever credential mechanism the final compose lands on).
- Don't enable the `loopback_users.guest = false` knob you'll see in stale tutorials.
- Don't expose `5672` (AMQP) or `15672` (management) on public ports. Tunnel for the admin UI.
- Watch DLQ size in `/metrics`. If it grows, it's not telling you "we have a queue", it's telling you "the worker is broken."

## Operator checklist before bringing up the stack

1. `openssl rand -base64 32 | tr -d '=+/' | cut -c1-32` — generate `REDIS_PASSWORD` and (later) `RABBITMQ_DEFAULT_PASS`. Paste into `backend/.env`. Do not check the file in.
2. Confirm `docker-compose.staging.yml` has no `ports:` mapping on `redis` (and later `rabbitmq`).
3. `docker compose -f docker-compose.staging.yml up redis` — wait for `healthy`. If it says `unhealthy`, the password env var is missing or the image is the wrong tag.
4. `docker compose exec redis redis-cli -a "$REDIS_PASSWORD" --no-auth-warning ping` returns `PONG`.
5. `docker compose exec redis redis-cli -a "$REDIS_PASSWORD" --no-auth-warning CONFIG GET maxmemory` should error with `unknown command` — that's the rename working.
6. From the host: `redis-cli -h 127.0.0.1 -p 6379 ping` should fail (connection refused or timeout). If it succeeds, the port is exposed and step 2 didn't take.
7. After RabbitMQ lands: same checklist for `5672` and `15672` from the host.

## When to revisit this doc

- Adding a new public port to any of these services.
- Moving any of these services off the same VPS.
- Adding a second app that talks to the same broker (then vhost/ACL story matters).
- Anything in `backend/.env` is suspected to have leaked.
